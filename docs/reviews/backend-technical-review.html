کیفیت کد و معماری

Fastify routes←services←shared-types و Prisma

تفکیک مسیرها، سرویس‌ها و منطق خالص مشترک شروع خوبی برای یک بک‌اند یکپارچه است. ورودی‌های اصلی با Zod بررسی می‌شوند، نقش و مالکیت نشست در سمت سرور کنترل می‌شوند، سؤال قبل از ارسال به کاربر پاک‌سازی می‌شود و امتیاز و گزارشِ پایان اجرا ذخیره می‌شوند. ایندکس یکتای نشست باز و کنترل هم‌زمانی پاسخ نیز تصمیم‌های درست‌اند.

هزینهٔ نگه‌داری در چند فایل متمرکز شده است: sessions.ts حدود ۴۸۰ خط و progress.ts حدود ۳۰۰ خط، هم‌زمان کوئری، منطق دامنه و شکل پاسخ API را اداره می‌کنند. برای توسعهٔ بعدی، جداکردن تدریجی جریان‌های «شروع، پاسخ، تکمیل، گزارش» و «مهارت، پروفایل، رتبه» مفید است. این کار باید پس از تثبیت تضمین‌های داده انجام شود.

فوری

راز نشست در نبود تنظیمات، مقدار ثابت دارد

اگر SESSION_SECRET تنظیم نشده باشد، برنامه از مقدار ثابت موجود در کد استفاده می‌کند؛ فایل Compose هم همان مقدار را به‌عنوان پیش‌فرض دارد. در محیطی که با این پیش‌فرض بالا بیاید، اعتبار نشست‌ها به رازی وابسته است که محرمانه نیست.

اقدام: راز نشست را برای اجرا اجباری کنید، حداقل طول/کیفیت آن را هنگام شروع بسنجید و پیش‌فرض Compose را حذف کنید.

شاهد: apps/api/src/middleware/requireAuth.ts:8 · apps/api/src/server.ts:48 · docker-compose.yml:48

فوری

تکمیل سناریو و ثبت پاداش یک عملیات اتمیک نیست

ابتدا نشست به completed تغییر می‌کند، بعد XP مرحله و پاداش روزانه ثبت می‌شوند. اگر ثبت پاداش یا کارهای بعدی خطا بدهد، نشست کامل می‌ماند اما پاداش ممکن است ناقص باشد؛ درخواست دوبارهٔ پاسخ هم با وضعیت ۴۰۹ رد می‌شود. تراکنش داخل سرویس پیشرفت، خودِ تغییر وضعیت نشست را پوشش نمی‌دهد.

اقدام: تغییر وضعیت نشست و اعتبار اصلی را در یک تراکنش قرار دهید. محاسبهٔ مدال/تداوم فعالیت را تکرارپذیر و قابل بازیابی کنید و تست شکست در هر گام بنویسید.

شاهد: apps/api/src/routes/sessions.ts:258–276 · apps/api/src/services/gamification.ts:270–324

مهم

ویرایش محتوا می‌تواند امتیاز مهارتِ اجراهای قدیمی را عوض کند

واردکردن مجدد یک سناریو، گراف سؤال و پاسخ‌نامهٔ همان رکورد را جایگزین می‌کند. صفحهٔ مهارت و پروفایل عمومی، مسیر تصمیم‌های گذشته را با گراف فعلی دوباره می‌سنجند. در نتیجه تغییر گزینهٔ برتر، مرحلهٔ مهارت یا حذف سؤال می‌تواند پروفایل کاربر را بدون اجرای تازه تغییر دهد؛ این در حالی است که امتیاز پایان سناریو به‌درستی snapshot شده است.

اقدام: نسخهٔ سناریو را به نشست وصل کنید یا شواهد امتیازدهی هر تصمیم را هنگام ثبت ذخیره کنید؛ سپس پروفایل را از همان شواهد تاریخی بسازید.

شاهد: apps/api/src/routes/admin/challenges.ts:78–82 · apps/api/src/routes/progress.ts:112–150 · packages/shared-types/skills.ts:303–315

مهم

درخواست‌های هم‌زمان می‌توانند AI را چند بار فراخوانی کنند

برای ارزیابی نهایی، دو درخواست می‌توانند پیش از ذخیره‌شدن نتیجه هر دو وضعیت «هنوز ارزیابی نشده» را ببینند و هر دو مدل را صدا بزنند. در پاسخ تشریحی هم فراخوانی مدل پیش از قفل ثبت پاسخ انجام می‌شود. پیامد آن هزینهٔ اضافه و مصرف ظرفیت است.

اقدام: برای هر ارزیابی وضعیت یکتای pending / ready / failed و قفل یا صف کار تعریف کنید؛ سپس محدودیت تعداد درخواست و سقف مصرف هر کاربر اضافه کنید.

شاهد: apps/api/src/routes/sessions.ts:202–239 · apps/api/src/routes/sessions.ts:422–472

مهم

تست‌های API در مسیر پیش‌فرض تست اجرا نمی‌شوند

سه فایل تست واحد در API وجود دارد، اما بستهٔ apps/api اسکریپت test ندارد. بنابراین فرمان تست ریشه، این تست‌ها را به‌طور خودکار اجرا نمی‌کند. برای مسیرهای حساسِ نشست، پاداش و احراز هویت هم تست شکست میانی و رقابت درخواست‌ها کم است.

اقدام: تست‌های API را به اسکریپت بسته و CI وصل کنید؛ سپس تست‌های دیتابیسی برای اتمیک‌بودن، تکرار درخواست و تغییر نسخهٔ سناریو اضافه کنید.

شاهد: apps/api/package.json:7–14 · package.json:7 · apps/api/src/services/*.test.ts

میانی

محاسبهٔ مهارت با تعداد اجراها بزرگ می‌شود

درخواست‌های مهارت، درخت مهارت و پروفایل عمومی تمام نشست‌های کامل کاربر و گراف سؤال‌های مربوط را می‌خوانند و در حافظه تجمیع می‌کنند. برای کاربری با تاریخچهٔ طولانی، زمان پاسخ و حجم دادهٔ خوانده‌شده رشد می‌کند.

اقدام: پس از درست‌شدن نسخه‌بندی تاریخچه، تجمیع افزایشی یا snapshot قابل بازسازی برای مهارت‌ها بسازید و برای داده‌های ریز صفحه‌بندی بگذارید.

شاهد: apps/api/src/routes/progress.ts:112–150 · apps/api/src/routes/profile.ts:65–69

میانی

مسیر سلامت، آماده‌بودن دیتابیس را نشان نمی‌دهد

/health همیشه ok برمی‌گرداند و بررسی سلامت کانتینر نیز همین مسیر را می‌خواند. پس در قطع اتصال PostgreSQL، API ممکن است سالم گزارش شود ولی درخواست‌های واقعی خطا بدهند.

اقدام: liveness و readiness را جدا کنید و در readiness یک بررسی سبک اتصال دیتابیس انجام دهید.

شاهد: apps/api/src/server.ts:52–53 · docker-compose.yml:65–71

ترتیب پیشنهادی اصلاحات

  1. بستن تنظیمات حساس اجرا. راز نشست اجباری، بررسی محیط هنگام راه‌اندازی، سپس readiness واقعی.
  2. درست‌کردن پایان چالش. تراکنش یا سازوکار جبران، همراه با تست خطای میانی و درخواست هم‌زمان.
  3. پایدارکردن تاریخچه. نسخه‌بندی سناریو و شواهد مهارت پیش از توسعهٔ محتوای زنده.
  4. کنترل AI. کار یکتا برای هر ارزیابی، محدودیت مصرف، سپس جداسازی فرآیندهای طولانی در صورت نیاز.
  5. تقویت چرخهٔ توسعه. اتصال تست‌های API به فرمان اصلی و CI، بعد بهینه‌سازی تجمیع و کوچک‌کردن فایل‌های بزرگ.

دامنه و شواهد بررسی

نوع‌سنجی API با tsc --noEmit موفق بود. ۴ فایل تست بستهٔ shared-types و ۳ فایل تست واحد API با اجرای مستقیم Node موفق بودند. ساختار مسیرها، سرویس‌ها، مدل Prisma، مهاجرت‌ها، Compose و فرمان‌های پروژه بررسی شدند.

این گزارش بازبینی ایستای کد است. تست‌های سرتاسری اجرا نشدند چون دادهٔ پایگاه موجود را تغییر می‌دهند. رفتار زیر بار واقعی و وضعیت عملیاتی محیط استقرار در این ارزیابی اندازه‌گیری نشده است.
